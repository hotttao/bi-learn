# 008 · S8：行数增长、目录增长与业务语义

## 先声明实验，而不是事后挑答案

S7 已确认并提交为 `1b0f9ec`。当前 S8 已完成本轮研究和完整检查，待用户 review，未提交。自动语义同步、并发编辑保护、部门权限继续按用户要求暂缓。

计划先于造数和查询写入 [s8/plan.json](../s8/plan.json)。所有 shell 命令从原型根目录执行。本步有两个独立变量：行数增长测引擎，目录增长测上下文和关系理解，不用百万行证明 Agent 会理解百张表。

- 数据行数：1 万、10 万、100 万订单，独立 PostgreSQL schema，通过既有 Trino 和 Wren 查询。每档另有退款和客户。
- 目录规模：10、100、500 个模型。7 张真实业务表外，其余是指向空 stub 的合成噪声别名，不声称造了 500 张真实业务表。
- 数值答案由 Python 整数分账本独立计算；比较总额、当前行业和十月日趋势。首轮单记，之后运行 5 轮，比较中位数和范围；没有清除数据库/操作系统缓存，不叫“冷查询”。
- 单查询探索目标：后续 5 轮中位数不超过 5 秒。超过就记录未达标，不隐藏；五个样本不提供可靠 P95。
- Agent 对照：500 模型下，3 个问题，各 2 次独立会话，两种条件使用同样模型配置、数据和只读 MCP 工具，仅业务规则文本不同。只在 schema-only 下澄清不等于算对数值，也不等于失败的安全行为。

当前机器总内存约 7.9GB，开始时 available 约 3GB，已有服务和 swap 活动；本实验不能当作独占机器的容量认证。Trino 限 2GB，业务 PostgreSQL 限 384MB。实施过程中会保留未达到目标和不可采集的指标。

## 第一步：先统一业务词汇与允许关系

用 [术语词典](../../../docs/ddd/bi008/CONTEXT.md) 区分净收入和财务确认收入、当前行业和下单时行业、可重叠标签和可相加分类。具体关系审阅清单在 [semantic-map.yaml](../s8/semantic-map.yaml)，它不是 Wren 自动识别的新建模语言，也没有自动转换成 MDL。供 MCP 读取的文字规则在 `s8/rules.md`：先写身份、粒度，再写关系角色、键、基数、缺失/历史规则与金额分配，最后写指标。

这是分析读模型，不推断订单/客户的交易聚合，也不为纯查询组合建立跨服务写 Workflow。原主 Wren 没有行业历史，本步仅在独立 S8 fixture 中提供历史表并验证；不偷改主项目能力。

六笔订单的独立净额为 150、140、300、100、80、95，总额 **865**。其中 A/1 从软件行业变为零售；A/3 缺少客户；A/1 同时属于 VIP、战略标签；同一订单有多笔退款，订单明细也有多行。另有财务确认表，其数字不能冒充净销售额。

| 分析语义 | 预期关系与结果 |
| --- | --- |
| 当前行业 | 部门＋客户 ID；A/1 所有订单当前归零售，软件 300、零售 245 |
| 下单时行业 | 同一身份＋业务日期处于 `[valid_from,valid_to)`；软件 450、零售 95 |
| 重叠标签 | 一行一订单净额再关联标签；VIP 385、战略 545、普通 100、无标签 80 |
| 标签组相加 | 1110，不能替代不重复基础总额 865 |

预期答案见 [expected-relations.json](../s8/expected-relations.json)。字段和类型不能确定上述选择，业务规则需要有人确认。

## 第二步：独立造数和构建

```bash
sudo .local/wren-venv/bin/python scripts/prepare_s8.py
```

只创建 `bi008_s8_10000`、`bi008_s8_100000`、`bi008_s8_1000000`、`bi008_s8_relations` schema，给既有只读角色授予这些 schema 的 SELECT。主销售表、crm.public 客户和主 Wren 源文件不改。

每档有 2 万客户记录，订单 80% 左右在 A 部门；日期覆盖 2026 年，四分之一订单有两笔退款。固定种子参与整数公式，实付/退款精确到分。先由独立 Python 循环写 [expected-scale.json](../s8/expected-scale.json)，再通过 PostgreSQL generate_series 造数，不用被测聚合 SQL 自证答案。

各档 Wren 项目放在忽略的 `.local/s8/projects/`。目录对照项目在 `.local/s8/catalogs/`，两条件的 MDL 一致，都是原始业务模型，未在其中额外定义计算指标或关系；仅 knowledge/rules 不同，规则正文来自 [s8/rules.md](../s8/rules.md)。这隔离了“读取文字规则”的作用，不把它与引擎强制关系混成一项。行数计时则使用复制自 W1 的可执行订单语义模型。两种实验基于原生 Wren 工具，不开发新 Agent。重复准备保留已有 schema，若订单数不符拒绝覆盖，不重置未知数据。

## 第三步：查询计时与上下文核查

```bash
.local/wren-venv/bin/python scripts/benchmark_s8.py
.local/wren-venv/bin/python scripts/inspect_s8_catalog.py
```

计时范围是 Wren Python SDK 的规划、执行、取数，不包含 Codex 推理或网页渲染；查询并发为 1。每轮核对账本，另执行展开后的 SQL 采集 Trino query ID、统计和可取得的内存/输入量。连接器下推后的 Trino 输入量不是数据库实际扫描量，二者不能混称。百万档分布式计划中，订单 TableScan 带 order_date constraint；退款侧仍有全量聚合。这说明缩小订单日期不一定同步缩小退款读取，后续性能治理应从实际计划出发。

`inspect_s8_catalog.py` 通过真实 stdio MCP 读取 10/100/500 模型的上下文；明确当前 grep 后端返回 full schema，不伪称按业务域或向量检索已经生效。同时运行错误关系对照和历史区间重叠检查。

## 第四步：真实 Codex 对照

```bash
.local/wren-venv/bin/python scripts/evaluate_s8.py
```

每题在仓库之外的临时目录创建一致的分析指令，避免父级 S7 指令泄漏净收入规则或 245。复用现成 Codex，关闭 shell/unified_exec/multi_agent，使用相同只读 Wren MCP 工具清单；不继承 Superset 资产写入工具，不改全局配置。

schema-only 可以选择澄清；schema＋规则需要实际执行并返回当前行业、下单时行业、标签金额。验证器分别统计数值正确、澄清、执行失败和工具调用/token 使用，不以猜对一个总额宣称懂了所有关系。原始 CLI 事件只保留在忽略目录；证据保存工具参数/结果和最终回答，不保存推理文本。

## 第五步：先读已完成的行数与关系结果

### 单查询耗时和正确性

| 订单数 | 总额首轮/后续中位 ms | 当前行业首轮/后续中位 ms | 十月日趋势首轮/后续中位 ms |
| --- | ---: | ---: | ---: |
| 10,000 | 843.16 / 521.45 | 495.73 / 461.71 | 373.60 / 357.09 |
| 100,000 | 345.27 / 452.61 | 1070.72 / 574.45 | 381.23 / 333.38 |
| 1,000,000 | 2167.20 / 1437.15 | 2153.63 / 1812.75 | 1136.45 / 907.40 |

9 组查询各 6 轮，共 54 次 SDK 查询均逐次对账；另有 9 次展开计划统计查询，不混入上表的中位数。全部达到预先声明的 5 秒探索目标。10 万首轮比后续快，说明不能把顺序第一次当成冷缓存；机器调度和既有缓存都会影响小样本。

百万行的另一次展开 SQL 采样中，Trino 报告的查询峰值内存约为总额 13.76MB、行业 15.22MB、日趋势 9.60MB；这不是数据库或容器总内存。[benchmark.json](../evidence/s8-benchmark.json) 保留每轮耗时、计划、结果、query ID 与 statement stats。`/v1/query/{id}` 额外明细接口返回 401，没有扩大身份去取；已可从 statement stats 得到本次查询峰值。physicalInputBytes=0 不等于 PostgreSQL 没有扫描，源端逐查询磁盘扫描和 CPU 仍未单独采集。

[资源快照](../evidence/s8-resource-snapshot.json) 是计时结束后的单次容器观察，不能作为逐查询负载或整个实验峰值。分布式计划另见 [s8-plans.json](../evidence/s8-plans.json)。

### 目录扩大时，哪些信息变大

真实 MCP get_context 返回 full schema：10 模型 1493 字节，100 模型 16505 字节，500 模型 83225 字节。两条件 schema 完全相同，规则分别为 89 / 1416 UTF-8 字节。这里字节数不是 token 数；实际模型调用 token 使用另在对照证据中记录。

当前没有按主题缩小上下文，也没有验证向量检索。因此不能说“用了 Wren，表多了会自动整理好”；它提供可维护语义和消费接口，但项目划分与检索范围仍需设计。噪声模型共用一张空 stub，只模拟目录文本量，不模拟 500 张真实表的发现和映射成本。

### 错误关系为什么不能靠总额一句话验收

| 错误路径 | 实际错误总额 | 正确基础总额 | 原因 |
| --- | ---: | ---: | --- |
| 原始退款直接关联订单后求实付减退款 | 1065 | 865 | 多笔退款重复累计同一订单实付 |
| 客户只用 customer_id 关联 | 1650 | 865 | A/B 部门复用客户 ID，匹配出多行 |
| 标签组金额直接相加 | 1110 | 865 | VIP 与战略允许重叠，组间不具可加性 |

正确当前行业、历史行业、重叠标签均与独立答案一致。行业历史区间当前无重叠；质量检查只证明本 fixture，没有冒充已做变更注入后的历史质量回归。见 [s8-catalog.json](../evidence/s8-catalog.json)。

## 第六步：表多以后，实际怎样组织关系

1. 先给问题选分析主题，例如销售净收入。列出必须的订单、退款、客户信息，不先把所有表连成一张大图。
2. 每个实体登记身份与粒度，客户是部门＋客户 ID，不能仅因字段名相同就关联。
3. 同一实体可有不同关系角色：当前行业走客户当前表，下单时行业走历史有效区间；这两条路径不能互换。
4. 关系旁登记消费规则：退款先聚合；缺失维度保留订单；标签允许重叠，组间金额不能相加；历史区间不能重叠。
5. 指标登记单位、时间和适用范围，建立模型、规则、独立答案的发布包。把这些通过 MCP 供 Codex 按需读取。
6. 目录继续增加时再拆分主题项目或设计受控主题检索；对无法命中的问题说明缺口，不能随便选一张金额表。本次只测到 full-context 的增长，没有将主题检索写成已完成能力。

维护时，DDL 变化只是信号之一；行业改为历史口径、标签改为分摊，即使字段不变也需要业务规则变更。关系应有负责人、依据、质量检查和消费资产清单。当前 owner 只是实验作者，不冒充公司业务负责人；自动同步和生产发布服务按用户要求不在本步处理。

本次复合键、聚合、时间区间和标签组规则可以用显式关系契约及 SQL 表达，没有需要推理的分类/传递规则，因此本步不部署本体或图数据库。这是对当前 fixture 的工程取舍，不是证明所有公司都不需要本体。真实跨域概念映射或规则推理出现时，再挑具体问题做对照。

## Agent 对照与最终交付

12 次真实 Codex 调用已完成。两条件的数据、MDL、模型配置、工具范围和问题相同，只有审核规则文本不同；每题各两次独立会话。

| 条件 | 数值正确 | 澄清 | 工具调用总数 | CLI 总耗时秒 | 累计输入 / 缓存输入 / 输出 token |
| --- | ---: | ---: | ---: | ---: | ---: |
| schema-only | 0/6 | 6/6 | 43 | 216.822 | 542331 / 355840 / 2553 |
| schema＋规则 | 6/6 | 0/6 | 69 | 340.626 | 1381510 / 1144704 / 8130 |

schema-only 的 0/6 是**数值答复覆盖**，不是指模型犯了六次数值错误；它缺少指标和关联口径时选择澄清，是合理行为。schema＋规则的 6/6 是本 fixture、三个问题、两次重复的观察，不当作稳定正确率。实际 SQL 都经过 dry_plan/dry_run，查询结果与独立分组/总额逐项核对。

CLI token 是多次工具往返中的累计计数，缓存输入是输入的子集，不能再相加；同一 schema 会在后续往返中重复进入上下文。实际模型耗时含工具等待和模型生成，不能与 SDK 单查询毫秒数混用。本机使用既有账户，未将这些计数换算成未知的实际人民币账单。因为带规则的条件真正做了查询，调用和耗时更多，不能直接用两行比较“规则让推理更贵或更便宜”。

结果见 [对照汇总](../evidence/s8-agent-comparison.json)，每个 trial 都有独立去敏工具/回答证据。原始事件保留在忽略的 `.local/`。汇总新增严格的实际分组对应核验后，用 `--collect-only` 重读了原始记录，没有重跑模型或改答案。

## 运行失败、停止和清理

本次没有需修复的造数、查询或模型执行失败；额外 query-info 401 已如实记录，statement stats 提供了可用替代指标。首次/后续耗时的波动属于观察结果，不通过重复筛选样本使其好看。

中断 Agent 测试时，只读 MCP 不会改业务表；重跑默认复用已完成 trial。中断造数时每个 schema 的 DDL/数据在一个事务内完成；已提交 schema 保留，后续重复准备会核对订单数，不盲目重置。修改业务规则后应重新构建并单独标记新试验，不能把旧证据当新版本的结果。

实验 schema 与 `.local/s8` 目前保留以便 review，不自动删除。无需本步数据时，可在停止实验查询后，由部署者只撤销/删除 `bi008_s8_10000`、`bi008_s8_100000`、`bi008_s8_1000000`、`bi008_s8_relations` 四个 schema，再删除 `.local/s8`；不得删除 `crm.public`、`sales` 或 Docker 数据卷。删除将丢弃本步合成数据，需要重新准备才能复现。普通停止沿用既有 Compose 服务流程，无须新增常驻服务。

## 当前工程结论与未验证项

单机、单一 PostgreSQL 源、单并发的百万订单达到探索目标，不代表 MySQL＋PostgreSQL 跨源生产场景、并发容量或 SLA。首次不是严格冷缓存，五次不足以报告可靠 P95；源端逐查询 CPU/磁盘负载未测。未来性能瓶颈应先看日期下推、退款汇总范围、执行计划和负载，再决定汇总表、副本或汇聚仓库，不能由这四组时间直接决定选型。

本次业务含义仍来自人为核实的规则。未做真实 500 表接入、向量/主题检索、公司实体匹配、自动语义同步、生产认证、并发资产修改或形式化本体推理。关系增长当前可由身份＋角色＋基数＋时间＋分配＋质量回归表达，所以不新增图数据库/本体系统；真正出现跨域概念冲突或推理需求后，再按具体问题验证。
