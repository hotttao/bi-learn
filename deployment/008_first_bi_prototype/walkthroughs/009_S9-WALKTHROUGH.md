# 009 · S9：Skill＋文件 Wiki 增量读取语义，Wren 只负责查询

日期：2026-10-18。S9 后续已由用户确认提交为 `9f73f7b`，下文保留实施时的操作与证据。本步接续已提交的 S8（`57f67a7`），按用户最新建议，把主要路线从“主题 MCP 返回元数据”调整为“文件 Wiki＋Skill”。实际结果见下文证据；保留早期 MCP 路线作为对照，不将其未完成的模型实验记为通过。

## 1. 先理解：可以，而且不需要向量检索

你提出的链路可行：Codex 已经能阅读文件，也已经是通用 Agent，不必为了取几个模型再开发一个 Agent 或引入向量库。给它一个小索引，让它沿主题、指标、关系的链接读取所需文件即可。

```mermaid
flowchart LR
  Q[用户问题] --> S[Skill 读取约定]
  S --> I[Wiki 主题索引]
  I --> B[相关指标与关系页]
  B --> Y[原生 Wren YAML]
  Y --> C[Codex 生成 SQL]
  C --> P[查询 MCP: dry_plan / dry_run / run_sql]
  P --> W[Wren / Trino / 只读业务源]
```

这里省掉的是元数据 MCP 调用，不是查询 MCP。文件读取仍是工具调用，也消耗上下文；不能提前承诺一定更便宜或更快。索引很大时，可先按业务域分层，再按指标和实体缩小范围；代码检索 `rg`、确定性名称/标签映射也可以先于向量检索使用。

组织方式参考 [Karpathy 的 LLM Wiki 思路](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)：保留来源，维护整理页和索引。但本实验将正式语义发布与普通查询分开，查询会话不能自由改写已审核口径。Skill 的按需加载方式参考 [OpenAI 官方 Skills 说明](https://developers.openai.com/plugins/concepts/skills)。我们用明确的本地 Skill 路径运行，不依赖未经验证的自动发现行为。

## 2. 谁保存什么，避免两份真相

| 文件/组件 | 责任 | 不承担的责任 |
| --- | --- | --- |
| 原生 Wren `models/<模型>/metadata.yml` | 字段、结构和 Wren 已实现的执行定义 | 从业务人员脑中自动发现关系 |
| `wiki/index.md` | 业务主题导航与歧义提示 | 枚举全部字段或所有两两关联 |
| `wiki/metrics/` | 指标含义、粒度、时间和金额规则 | 替代可执行计算模型 |
| `wiki/relationships/` | 按分析目的解释关联路径、基数、历史归属、缺失和可加性 | 靠提示词证明权限隔离 |
| `raw/` | 审核来源；生产中可关联 DDL、报表、需求和业务负责人 | 把原始资料直接当权威指标 |
| Skill | 如何选主题、增量阅读、发现歧义、规划查询 | 自己充当另一份业务规则库 |
| `release.json` | 文件指纹、模型版本绑定和发布标识 | 签名认证、自动理解业务变化 |

原生 YAML 不转换成另一份自创 schema。Wiki 用链接指向它，字段和表达式的结构定义继续在 Wren 中维护。关系页记录“这个关系用于什么问题”，例如同样是客户行业，“当前行业”和“下单时行业”应当是两条明确路径。

需要特别区分：本轮复用 S8 的**原始模型目录**来隔离上下文读取方式；部分业务规则仍由 Codex 根据文字生成 SQL，Wren 校验并执行。它们尚未全部成为 Wren 强制执行的关系或指标。文件导航正确不能证明任意 Agent 都会生成相同口径。核心、复用频繁的指标应继续落成可执行定义和回归测试；主 W1 项目的可执行建模实验仍保留。

## 4. 如何亲眼确认“自己按需读取”

读 `evidence/s9-wiki-current_industry-1.json` 中的 `file_commands` 和 `calls`：

- 文件命令先读 Skill，再读 `wiki/index.md`，然后沿主题页读取基础指标及模型。
- 当前行业仅需订单、退款、当前客户 3 个模型；历史行业把客户模型换为行业历史；标签分析则换为标签成员。
- MCP 只出现 `bi008_s9_query` 的查询工具，没有 `get_context`、`list_models`、`describe_model`。
- 每条执行 SQL 前存在对应的 `dry_plan` 和 `dry_run`。最终回答之外，还检查了实际查询结果，而非只看模型自述成功。

实测结果：三类问题各两次，六次全部正确；每次读取 3 个相关模型、4 次文件调用，共 24 次文件调用、31 次查询 MCP。没有元数据 MCP 调用。六次累计耗时 380.619 秒，S8 全量 schema＋规则历史对照为 340.626 秒，本轮没有证实提速。累计输入 token 为 1,317,025（其中缓存输入 1,129,088），输出 7,944；缓存输入属于输入子集，不能再次相加。两轮环境和工具条件不同，也不是随机对照，不能据此给出生产成本结论。

汇总见 [文件 Wiki 实验](../evidence/s9-wiki-comparison.json)，单次证据保留实际读取内容、SQL、工具返回、最终答案与累计 token 计数，不保存内部推理。六次小样本只证明这些案例的可行性，不代表未知业务问题的稳定正确率。

## 5. 文件变多、关系变化以后如何维护

不要为每两张表写一份关系，也不要让 Skill 堆满全部业务知识。先维护稳定业务实体与指标，再为明确分析目的记录可用关系：客户身份键是什么、订单是什么粒度、行业在哪个时点、标签是否允许重叠。共享规则只写一次并链接。

本体并非这条链路的前置条件。先建立实体、属性、关系角色、时间、粒度和来源；如果以后出现跨域实体对齐、多跳规则推导或机器推理需求，再引入更正式的本体及治理流程。Markdown 链接本身不会提供这些推理保证。

变化处理需要两条来源：数据库 DDL/注释/血缘帮助发现结构变化；业务负责人确认口径变化。schema 不变，也可能发生“当前行业改为历史行业”的定义变化。建议形成候选变更→列出受影响主题/模型/指标→审核→编译与固定问数回归→发布一致版本→保留回退版本的流程。当前只实现本地手动发布和一致性拒绝，没有实现生产增量采集或自动同步。

本次 `verify_s9_wiki.py` 在一次性副本中分别删除主题页、修改原生 YAML、修改指标规则、替换执行版本引用，四种情况均拒绝；正式发布包保持不变。工具列表也通过真实 stdio MCP 核查为仅三个查询工具，见 [一致性与工具证据](../evidence/s9-wiki-controls.json)。

发布包必须来自经过审核的环境；本地 SHA 校验只能发现意外混版，不能阻止有权同时改文件和清单的人。文件读取和主题导航也不是访问控制：当前查询服务仍允许原生已审核目录内模型，不限制为当前主题的 3 个模型；本轮是读取行为验证，不能当部门隔离证明。

生产发布应切换独立版本目录，避免原地改文件造成查询竞态；本实验的逐次指纹预检不构成原子发布协议，也不恢复已暂缓的并发编辑保护。

已有成功单次证据时 evaluator 默认复用；它不是每次运行都重新采样。要做新一轮独立样本，应另建输出版本并记录条件，避免覆盖旧证据。`--collect-only` 只重新解析本机已有原始日志，不重新调用 Codex。

查询 MCP 是启动器的 stdio 子进程，问答结束后退出，不新增常驻端口。实验发布、日志和临时副本位于忽略目录；版本化 Wiki/Skill 源码和脱敏实验结果留在本目录。底层原有服务保持运行，未更改主 245 基线、S7 日期看板或用户全局配置。部门隔离、自动 Wren→Superset 语义同步、并发 BI 编辑保护及真实网络故障恢复仍未实现。
