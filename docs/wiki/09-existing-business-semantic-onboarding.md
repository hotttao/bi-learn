# 将存量业务数据库整理成 Agent 可用的 schema 与语义层

日期：2026-10-16。本文记录存量业务接入的方法、候选工具与实验计划；尚未连接公司数据库，尚未验证这些工具在本项目的效果。

承接 [首个 BI 原型](08-first-bi-prototype.md)、[业务工作流](workflow.md) 和 [语义层调研](agent-semantic-research.md)。现有原型先用固定测试数据学习 BI；本文补充另一项必要研究：当表和业务已经存在、关系并不清楚时，如何发现、验证并发布语义。

已有工具如何分别承担语义维护、变化发现及发布同步，以及下一轮关系变更实验，见 [业务语义维护与工具分工](10-semantic-maintenance-tool-selection.md)。本文侧重首次接入，该文侧重持续维护。

## 1. 造数实验尚未回答什么

造数时我们事先知道订单、退款和客户的关系，因此能直接写出正确 SQL。它验证的是“已知关系能否被正确执行”，不能证明 Agent 能从陌生的公司数据库中自动恢复业务含义。

存量接入需要一条独立流程：**自动采集结构 → 从已有代码和报表提取业务规则 → 检查数据 → 业务人员审核 → 发布语义模型 → 用真实问题回归。** 不必从头人工描述每一张表，也不能把自动生成的关系直接当成事实。

## 2. 分清三种信息

| 层次 | 例子 | 获取方式与边界 |
| --- | --- | --- |
| 物理 schema | 表、字段、类型、主键、外键、注释 | 从数据库元数据采集；没有声明的外键、错误或过时注释不会自动变正确 |
| 业务关系 | 订单关联付款客户还是下单客户；客户 ID 是否只在租户内唯一 | 从约束、代码、现有 SQL 和数据检查中提取候选，再审核 |
| 指标与业务口径 | 有效订单范围、是否含税、退款归属时间、部门归属 | 从业务规则、报表和负责人处确认，形成可执行、可版本化定义 |

例如 `status` 是整数属于 schema；`status=4` 表示退款完成属于业务含义；退款完成的订单是否计入销售额属于指标口径。仅扫描字段类型不足以回答后两者。

还要区别“数据血缘”和“可查询关系”：A 表由 B 表加工而来，不等于 A 与 B 可以直接 JOIN；现有 SQL 使用了某条 JOIN 路径，也不等于该路径适用于所有指标。

## 3. 候选工具分别负责什么

| 工具 | 能力定位 | 适合本项目的用途 | 不能直接推定的能力 |
| --- | --- | --- | --- |
| OpenMetadata | 元数据采集、血缘、使用情况、数据剖析和质量工作流 | 库表很多时建立数据目录，持续整理资产和检查结果 | 采集目录不等于已生成可执行的正确指标；各连接器能力需逐项核实 |
| Wren MDL 建模工具 | 将源 schema 整理为模型、关系、计算字段和业务知识 | 试验从现有数据库生成 Agent 可读的语义项目，再审核和补充口径 | 自动生成的模型不能确定权威表、状态含义或完整业务规则 |
| Cube | 定义指标、维度、关联、预聚合和访问策略 | 多个应用需要共用同一套指标计算时评估 | 定义模型不等于自动理解原业务，也不意味着任意实时跨源 JOIN |

OpenMetadata 官方采集框架覆盖 Metadata、Lineage、Usage、Profiler、Data Quality 等工作流，支持内部或外部管理采集任务。实际源库支持范围需按连接器检查。[官方采集说明](https://docs.open-metadata.org/latest/deployment/ingestion)

Wren 当前开源文档给出的流程是：连接数据库，使用其配套技能辅助生成 MDL 项目，review 后构建和索引。生成内容包括模型、字段、类型，以及连接器暴露外键元数据时推断出的关系；业务知识需要继续补充。文档明确说明，脚手架不能确定哪张客户表是权威表，也无法自行理解状态码等业务含义。[官方建模说明](https://docs.getwren.ai/oss/guides/model)

Cube 的模型包含 measures、dimensions、joins、pre-aggregations 和 access policies，适合作为经过确认的业务定义的执行载体。[官方模型说明](https://docs.cube.dev/reference/data-modeling/cube)

**本项目的候选顺序：**如果问题是“如何生成 Agent 可读的语义模型”，先考察 Wren 存量建模流程；如果问题是“库表太多、资产与关系难以持续管理”，再评估 OpenMetadata；指标复用和统一执行成为明确需求后再评估 Cube。不同时部署三套系统。

这里引用的是当前在线文档，不是已固定版本的部署保证。试验前仍需固定版本、核对源连接器、许可证、认证方式及与 Trino/Superset 的集成边界。Wren 新版与历史聊天式产品的区别见 [WrenAI 独立分析](07-wrenai-analysis.md)。

## 4. 从公司的一张现有报表开始

建议选“每月各部门净销售额”这类已有稳定报表，从相关的 5～10 张表开始，不从全公司所有数据库开始。

### 第一步：收集证据

收集只读元数据或脱敏导出：DDL、字段注释、已有报表 SQL、视图、ETL、ORM 模型、状态枚举、业务说明、报表负责人及已有对账结果。

数据库能反映存储结构，应用代码能揭示状态和关联条件，报表 SQL 能暴露实际计算口径，负责人能说明选择这些规则的原因。证据冲突时保留分歧，不让模型自行挑一个“看起来合理”的定义。现有报表也可能有历史错误，需要核实。

### 第二步：生成带依据的关系草稿

工具提取结构，Agent 辅助整理候选关系和待确认问题。每条关系至少记录：

```yaml
# 内部研究记录示意，不是特定产品原生配置。
relationship: order_customer
source: orders
target: customers
join_keys: [tenant_id, customer_id]
cardinality: many_to_one
grain_before: one_row_per_order
grain_after: one_row_per_order
evidence:
  - existing_report_sql
  - application_customer_lookup
checks:
  - customer_composite_key_unique
  - unmatched_order_count
  - joined_order_count_unchanged
status: pending_review
```

实际记录应补充证据文件位置或查询 ID、采集时间、适用业务范围和审核人。字段同名、相似名称、数据值重合只能作为线索。若存在 tenant_id/dept_id 等范围键，必须检查是否应参与关联。

### 第三步：数据检查与业务审核分开做

| 数据检查回答 | 业务审核回答 |
| --- | --- |
| 客户复合键是否唯一？ | 这个指标应关联付款客户还是下单客户？ |
| JOIN 后订单行数和金额是否被放大？ | 测试、取消、内部交易订单是否排除？ |
| 缺失客户、空值、孤儿退款有多少？ | 缺失关系应保留、拒绝还是归为未知？ |
| 历史维度有效期是否重叠？ | 行业使用当前值还是订单发生时的值？ |
| 金额单位、类型和币种有哪些？ | 是否含税、汇率按哪个时点换算？ |

数据检查通过只能证明观测数据符合某些条件，不能单独证明业务含义。抽样发现的唯一性也不能替代完整检查或数据库约束。大型表的扫描需要安排预算和执行窗口。

### 第四步：发布小范围语义模型

每个已审核模型至少包含：实体和粒度、主键与允许关联路径、基数、空值和历史规则、指标公式、维度、时间与单位、权限适用范围、来源、负责人、版本和测试用例。

先发布一两个指标及其依赖表。未知含义保留为待确认，不为了覆盖所有表而填入猜测。发布的业务定义需要映射到实际可用的数据集或语义引擎模型；权限必须在查询服务和工具服务执行。

### 第五步：用报表和明细对账

固定数据快照或可解释的取数时点、时间范围及身份，比较已核实报表与新模型的结果。至少检查总额、分组、行数和差异明细；不能仅凭总额相同判定正确。

每个错误都需要定位：结构采集错误、关联错误、指标口径错误、数据质量问题，还是源数据更新造成的时间差。修正后添加回归用例。

## 5. 怎样交给 Agent 使用

### 起步：提供已审核上下文

把指标说明、允许关联、字段含义和正确/错误示例放在版本化文件中，Agent 按需读取，再通过受限工具查询。文档便于起步，但不能保证模型一定遵循，也不能代替 SQL、权限和成本校验。

### 进阶：通过语义模型执行

由 Agent 选择已定义的模型、指标、维度和过滤条件，语义引擎负责解析已建模的关系与计算。是否能完全限制原始 SQL、哪些调用路径经过模型，需要实际验证。

面对大量表，建议按以下路径逐步发现上下文：

```text
当前身份可用的业务域
  → 指标摘要与版本
  → 相关实体和允许关联路径
  → 必需字段、时间规则和示例
  → 核查部署中的真实模型
  → 受限查询与结果核验
```

MCP 提供工具访问方式，语义知识仍需采集、审核和发布。元数据目录、MDL 和 Superset 数据集之间不会仅因都支持某种接口就自动同步；需要明确 ID 映射、版本及更新机制，未验证前不声称已经打通。

## 6. 数据增长后如何维护，是否需要本体

行数增长重点检查扫描、过滤下推、索引、汇总和源库压力。表数与业务域增长重点检查实体身份、同名异义、关联和指标版本。这两类问题要分开实验。

每次 schema 或业务规则变化，都应做差异检测、定位受影响的模型/指标/看板、运行回归，然后发布新版本；不能自动把新字段和新表全部开放给 Agent。

本体可以形式化共享概念及其关系，OWL 也提供类、属性和形式语义。[W3C OWL 2 概览](https://www.w3.org/TR/owl2-overview/)

本项目暂不把本体平台设为前置条件。先把实体、关系、指标和约束落实为可审核、可测试的契约。只有当跨域概念映射、关系推理等需求明确出现，且当前模型难以表达时，再选一个具体问题比较本体方案。表多本身不是引入本体的充分理由；本体也不能自动补齐缺失业务知识或解决大表扫描。

## 7. 补充到原型的存量接入实验

该实验是待执行建议，不改变当前逐步 review 的约定，也不代表已获准访问公司数据库。保留原有造数实验用于理解组件与校验基础正确性；存量实验检验发现、审核和发布业务关系的过程。

输入材料：一个业务域的 5～10 张表的脱敏 DDL/注释、已有报表 SQL、业务说明，以及可对账的测试快照或脱敏样本。拿不到真实数据时，可以先验证元数据整理，但不能宣称真实业务对账通过。

| 实验环节 | 交付物 | 验收条件 |
| --- | --- | --- |
| 采集 | schema 清单与来源记录 | 表、字段、类型和已声明约束与源一致；缺失说明明确 |
| 关系恢复 | 候选关联、证据和待确认问题 | 能指出复合键、粒度与扇出风险；不把推断当事实 |
| 业务审核 | 指标与关系的确认记录 | 权威表、状态范围、时间、金额及权限口径已确认 |
| 发布 | 版本化语义模型与真实资产映射 | 模型可解析，必要质量检查通过，版本可追溯 |
| 问答对照 | 仅 schema 与 schema＋语义的同题结果 | 同身份、数据、模型配置及工具范围，独立会话运行；记录正确率、错误类型与成本 |
| 对账与变化 | 明细差异、schema 变更回归 | 合计与分组一致，失败可定位；变更不会静默破坏已有指标 |

评估不能只统计回答正确率，还应记录人工审核耗时、未解决歧义、错误关联数量，以及新表接入后需要改哪些模型。若 Agent 只记住固定答案，没有正确恢复关联，实验不能算通过。

下一次更新部署计划时，应将本实验作为独立 review 单元安排；先确认材料和验收范围，再决定是否增加 Wren 或元数据目录组件，不在基础 BI 尚未跑通时同时扩展全部工具。
