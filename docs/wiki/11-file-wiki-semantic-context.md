# 用文件 Wiki 与 Skill 向 Agent 提供业务语义

日期：2026-10-18。承接 [语义维护工具取舍](10-semantic-maintenance-tool-selection.md)；本地实现见 [009 · S9 操作教程](../../deployment/008_first_bi_prototype/walkthroughs/009_S9-WALKTHROUGH.md)。S9 已验证并提交为 `9f73f7b`。2026-10-19 新增第 5 节改进方案，仅规划、暂不实现。

## 1. 为什么可以绕过元数据 MCP

通用 Agent 可以直接阅读文件。将已审核的 Wren 原生模型与业务说明作为一个版本化目录提供给 Codex，通过 Skill 规定读取流程，就能采用：

**用户问题 → Skill → 业务域/主题索引 → 所需指标和关系页 → 相关 Wren YAML → 规划 SQL → 查询 MCP。**

不需要先做向量检索，也不必经 Wren MCP 的 `get_context/list_models/describe_model` 获取同一份模型。文件命令仍是工具调用，查询执行也仍需要受控入口；不能将“没有元数据 MCP”理解为“没有工具开销”。

参考 [LLM Wiki 原始思路](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 中的来源、整理页和索引组织方式，以及 [OpenAI 官方 Skills](https://developers.openai.com/plugins/concepts/skills) 的按需读取方式。本项目不引入名为 LLM Wiki 的新服务，也不让查询 Agent 自动发布正式指标。

## 2. 文件怎样组织

```text
发布包/
├── .agents/skills/bi008-semantic-context/SKILL.md
├── wiki/
│   ├── index.md
│   ├── metrics/net-revenue.md
│   ├── relationships/current-industry.md
│   ├── relationships/historical-industry.md
│   ├── relationships/overlapping-tags.md
│   ├── SCHEMA.md
│   └── log.md
├── raw/reviewed-sales-rules.md
├── wren/models/<model>/metadata.yml
└── release.json
```

Wren 原生 YAML 保存字段、结构和已经实现的执行定义；Wiki 链接 YAML，解释业务目的与关系角色；Skill 规定如何导航和遇到冲突时怎么办。不要在三处复制字段、公式与 JOIN 规则。

关系按业务问题组织，而非只写“订单表关联客户表”：当前行业与历史行业采用不同时间语义；退款先聚合回订单粒度；标签是可重叠成员，分组金额不能相加作为总额。主题页应明确身份键、基数、粒度、时间边界、缺失处理、可加性及审核来源。跨域增长时增加分层索引和共享实体入口，避免穷举任意两表关系。

不需要一开始上正式本体。先统一实体、关系角色和指标；出现跨域身份对齐、多跳规则推导等明确需求后，再评估本体及推理工具。文件链接可表达关系，但不自动提供本体推理。

## 3. 与全量 MCP 上下文的实测比较

S9 用现有 Codex CLI 在隔离工作区运行三种问题各两次，与先前 S8 的全量 schema＋规则组作历史对照。原生目录相同，包含 500 模型，其中多数是空表别名；不是 500 张生产业务表。S9 开放文件读取，S8 不开放，时间与调用差异不能只归因于索引方式。

| 指标 | S8 全量 schema＋规则 | S9 文件 Wiki＋Skill |
| --- | ---: | ---: |
| 数值正确 | 6/6 | 6/6 |
| 工具调用 | 69 次 MCP | 24 次文件＋31 次查询 MCP |
| 元数据 MCP | 使用 | 0 次 |
| 单题实际读取模型 | 全量目录上下文 | 3 个相关原生模型 |
| 六次总耗时 | 340.626 秒 | 380.619 秒 |
| 累计 input tokens | 1,381,510 | 1,317,025 |
| 其中 cached input tokens | 1,144,704 | 1,129,088 |
| output tokens | 8,130 | 7,944 |

本次确认了按需读取和结果可行性，**没有证实更快**。计数是 CLI 的累计使用量，缓存输入是输入的子集，不能再次相加或当作单次上下文大小；小样本不能推出稳定成本收益或生产正确率。实际调用与结果见 [S9 汇总证据](../../deployment/008_first_bi_prototype/evidence/s9-wiki-comparison.json)。

## 4. 最关键的取舍：维护责任仍然存在

| 问题 | 文件方案能做什么 | 仍需要什么 |
| --- | --- | --- |
| 怎么找到相关语义 | 人可审查的索引、链接和 Skill，按需阅读 | 正确的主题划分、别名与歧义处理 |
| schema 改了怎么办 | 校验已发布文件与 Wren source revision，一致性失败则拒绝 | 结构变更采集、影响分析、审核和重新发布 |
| 业务口径变了怎么办 | 在来源、规则页和变更记录中表达候选变化 | 业务负责人确认；DDL 无法证明业务含义 |
| 怎么保证计算一致 | Wren 执行定义和固定问数回归可约束结果 | 将重要文字规则落成可执行指标，不能只靠提示词 |
| 多人或多机器使用 | 发布一致的只读目录/版本包 | 分发、回退、可信来源及真正权限控制 |

S9 的文件指纹预检拒绝缺页、YAML/规则被修改和执行版本不一致，**不是自动同步或原子发布协议**。修改需产生候选版本，检查依赖与冲突，构建并运行回归，审核后发布一致目录；查询 Agent 只读已发布版本。不要原地让它边查边改正式规则。

本轮为隔离读取方式使用 S8 的原始模型，部分规则仍由 Codex 根据文本生成 SQL；Wren 并未强制实现全部业务口径。主 W1 的可执行语义实验继续保留。只要重要规则还只在 Markdown 中，少了一层元数据服务也不会自动消除错误 JOIN 或口径漂移。

文件读取适合当前可分发、可审核的独立原型。若日后需要跨机器动态发现、按身份裁剪元数据、统一服务多种客户端，元数据 MCP/API 仍有价值；向量检索可以是后续补充，不是当前前置条件。部门隔离、Wren→Superset 自动语义同步、并发 BI 编辑保护仍按用户要求暂缓。

## 5. Skill Review 后的改进方案（2026-10-19，仅规划）

**状态：待实施。用户要求先记录方案，暂不实现。** S9 原型已提交为 `9f73f7b`，根目录 `.codex/` 已提交为 `93f9fa2`。以下内容不代表已修改 Skill、索引、发布脚本或运行环境，也不代表新增能力已通过测试。

### 5.1 改进依据与实施顺序

当前 Skill 入口简短，指标、关系与原生模型分开维护，适合现有合成实验。需要补齐的是发布契约、依赖校验和索引增长验证。

| 顺序 | Review 发现 | 拟实施的改进 | 验收标准（待执行） |
| --- | --- | --- | --- |
| 1 | Skill 依赖外部工作区；修改源码后再次运行发布脚本仍保留旧包，缺少差异提示 | 明确语义包根目录、版本和查询工具；分开验证、候选构建、发布与版本选择 | 缺少语义包时明确报错；能识别源码未发布；旧版本仍可用；分析会话明确绑定一个版本 |
| 2 | 主题依赖写在自然语言里，发布器只检查链接存在 | 主题增加结构化元数据，从中生成索引并校验依赖 | 拒绝重复 ID、缺失依赖、循环引用和无效模型引用；共享依赖去重；废弃主题不能静默成为查询入口 |
| 3 | 来源链接未区分用途，两次历史行业实验都读取了完整规则文件 | 区分必读依赖与按需追溯；定位来源片段 | 普通查询不默认读取全部来源；追溯请求能读取对应证据；必要业务规则不能只藏在可选来源里 |
| 4 | 多主题组合没有明确的依赖合并和语义检查规则 | 合并依赖后核查身份键、粒度、时点及可加性 | 已定义组合查询正确；组合未定义或存在歧义时先澄清或报告缺口，不擅自拼接 JOIN |
| 5 | 500 模型目录只有 4 个索引入口，六个问题未充分考验主题辨别 | 增加相近主题、同义词、组合问题与不支持问题，分段测量 | 固定问题集上的主题、必需规则和结果符合预期；单独报告读取成本与发现耗时，不将模型数当作索引规模 |

优先实施第 1、2 项，形成一次可独立 review 的交付；通过后再做第 3、4 项，最后进行第 5 项对照评估。当前只有 4 个主题，无需立即增加多层目录。业务域增多后再拆为“总索引 → 业务域索引 → 主题”。这些是建议的后续边界，尚未获准开始实施。

### 5.2 语义包与发布契约

交付单位应是“Skill＋语义包＋查询连接配置”。Skill 可以继续独立维护，Wiki 与模型不必塞进 Skill 目录；启动入口负责明确本次语义包根目录及版本，Skill 按该入口阅读，不依赖碰巧正确的当前工作目录。

拟采用以下发布流程，名称表示操作职责，**尚不是已实现的命令接口**：

1. **检查状态**：比较当前 Wiki、Skill、模型和来源引用与已发布版本，分别显示一致、存在未发布修改或发布包损坏。源码变更不等于旧发布包损坏。
2. **构建候选**：在新目录收集同一版本的文件，生成索引，校验依赖和链接，绑定 Wren source revision 与 MDL 指纹。
3. **审核与回归**：展示变化主题及受影响指标，运行对应固定问数和必要数据质量检查。文件指纹只能证明一致性，不能证明业务含义正确。
4. **发布新版本**：审核通过后登记独立版本，保留旧包，避免直接覆盖查询中的文件。
5. **选择与回退**：分析会话开始时选定版本，并验证执行端模型一致；回退同时恢复相匹配的执行模型，不能只回退 Wiki。若旧模型不可用，应拒绝启动并说明原因。

验收应覆盖：修改 Wiki 未发布、修改 Skill 未发布、文件被意外修改、缺失入口、执行模型混版，以及显式选择旧版本。暂不引入生产自动同步、分布式发布或并发编辑机制。

### 5.3 主题元数据与索引生成

建议主题页采用轻量 frontmatter，正文继续解释业务语义。例如下列内容只是拟议格式，不要求 Agent 将它当作 Wren 模型：

```yaml
id: sales.historical_industry
aliases:
  - 下单时客户行业
  - 订单发生时行业
requires:
  - sales.net_revenue
models:
  - crm_industry_history
status: active
```

`requires` 引用稳定的主题/指标 ID，而不是随文件移动变化的路径；`models` 引用原生模型名，依赖主题提供的订单、退款模型不必在每个主题重复声明。生成器建立 ID 到文件的映射，展开依赖并去重，检测循环和失效引用。共享别名有歧义时应保留候选和澄清条件，不能强行分配给第一个匹配主题。

生成的索引只保留 ID、别名、简短用途、状态和入口，不复制完整字段或公式。主题页是元数据维护入口，生成索引不手工编辑，避免形成两份事实。关系正文仍需写清身份键、粒度、基数、时间、缺失处理及可加性；检查元数据完整不等于这些规则已经可执行。

### 5.4 按需读取与组合问题

拟在 Skill 中明确两类链接：

- **必读依赖**：当前主题、共享指标与本次查询需要的原生模型。合并依赖后批量读取，已读文件在同一版本的会话中不重复读取。
- **按需追溯**：原始资料、来源片段和历史变更。用户要求解释依据，或规则冲突、信息缺失时再读取；冲突不能由 Agent 自行裁定口径。

历史行业实验目前会读取完整 `raw/reviewed-sales-rules.md`。后续可保留完整来源，同时给规则建立稳定章节或片段定位；仅添加 Markdown 锚点并不能保证工具不读取全文，需要让实际读取方式支持片段选择。摘要必须覆盖查询必要规则，不能以节省上下文为由省略关联条件。

对于“按下单时行业和客户标签统计净收入”，读取历史行业、标签以及共同基础指标的依赖并集后，还需核查：客户身份是否一致、行业有效期是否唯一、标签是否扩行、分组是否允许重叠、总额从哪个粒度计算。依赖并集只解决读哪些文件，不证明两个维度可以直接组合。未经定义的组合应先报告缺口，不为了回答而临时发明业务规则。

### 5.5 如何验证索引效率

现有实测每题 4 次文件调用，当前行业约读取 5.2 KB、历史行业约 6.7 KB、标签约 5.2 KB；历史行业包含完整来源规则。六次模型问数全部正确，但 4 个主题与问题直接对应，尚未验证在大量相似主题中的选择能力。S9 总耗时 380.619 秒，S8 历史对照 340.626 秒，也没有证实提速。

后续评估应将“业务主题数量增长”与“模型文件数量增长”分开。建议准备 4、20、100 个主题层级的目录，加入有区别依据的相近候选，而非只增加不会被索引触及的噪声文件。规模是拟议实验条件，未实际创建。固定问题集至少覆盖：

| 问题类型 | 示例 | 预期行为 |
| --- | --- | --- |
| 明确单主题 | 按下单时客户行业统计净销售额 | 选择历史行业及基础指标依赖 |
| 同义表达 | 按订单发生时行业统计净收入 | 与对应标准问法选择相同语义 |
| 相近指标 | 净销售额、财务确认收入、毛利 | 区分定义；未支持指标不替代计算 |
| 歧义 | 按行业看收入 | 澄清影响结果的指标和时点 |
| 多主题组合 | 历史行业＋客户标签 | 检查组合语义；缺口先报告 |
| 跨域角色 | 客户、付款客户、签约客户 | 根据定义区分身份，不靠表名猜测 |
| 非法或过期入口 | 已废弃主题、缺失依赖 | 明确拒绝或引导已审核替代项 |

每题预先声明期望主题、必读规则、允许澄清项和是否可执行；预期答案不进入分析工作区。记录以下指标：

- 主题选择正确率、必要规则漏读率、应澄清时的处理正确率，以及错误替代未支持语义的次数。
- 实际读取文件、内容字节数、文件调用次数和重复读取量；不能只根据命令中出现的文件名证明读取范围。
- 从开始读取入口到语义选择完成的耗时，与 SQL 生成、规划校验、数据执行耗时分别统计；阶段无法可靠辨认时标注计时边界。
- 最终查询数值、粒度与总额正确性。涉及数据质量门槛的规则另做异常数据验证，不能只检查文档存在。

首先要求固定验收集不漏必需规则、不错误替代口径，依赖异常能被拒绝；性能目标在实际开测前锁定，并使用相同模型、相同问题和明确缓存条件做重复比较。既有六次成功结果保留为基线，不覆盖、不外推为生产正确率。
